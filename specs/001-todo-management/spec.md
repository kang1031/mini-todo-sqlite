# Feature Specification: 할 일 관리 (Todo Management)

**Feature Branch**: `001-todo-management`

**Created**: 2026-09-16

**Status**: Draft

**Input**: User description: "사용자가 할 일을 추가하고, 목록을 확인하고, 완료 여부를 토글하고, 삭제할 수 있는 기능이 필요하다. 할 일에는 제목(필수)과 완료 여부가 있다."

## Clarifications

### Session 2026-09-16

- Q: 이미 추가된 할 일의 제목을 나중에 수정(이름 변경)할 수 있어야 하나요, 아니면 이번
  기능 범위에서는 제목 수정이 아예 제공되지 않나요? → A: 제목 수정 기능은 이번 기능
  범위에서 제외한다(수정하려면 삭제 후 재생성).
- Q: 할 일 목록에 완전히 동일한 제목을 가진 항목이 여러 개 존재해도 되나요, 아니면
  제목은 목록 내에서 고유해야 하나요? → A: 중복 허용. 각 항목은 내부 고유 식별자로만
  구분되며 제목 중복 검사는 하지 않는다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 할 일 추가 및 목록 확인 (Priority: P1)

사용자는 새로운 할 일의 제목을 입력해 목록에 추가하고, 추가된 항목이 전체 목록에서
바로 보이는지 확인할 수 있다.

**Why this priority**: 할 일을 추가하고 눈으로 확인하는 것은 이 기능의 핵심 가치다.
이 흐름이 없으면 다른 어떤 기능(완료 토글, 삭제)도 의미가 없으므로 최소 기능 제품
(MVP)의 필수 조건이다.

**Independent Test**: 제목을 입력해 할 일을 추가한 뒤, 목록을 열어 방금 추가한
항목이 "미완료" 상태로 표시되는지 확인하는 것만으로 독립적으로 테스트할 수 있다.

**Acceptance Scenarios**:

1. **Given** 목록이 비어 있는 상태, **When** 사용자가 제목 "우유 사기"를 입력해
   할 일을 추가하면, **Then** 목록에 "우유 사기" 항목이 미완료 상태로 나타난다.
2. **Given** 이미 항목이 여러 개 있는 목록, **When** 사용자가 제목이 비어 있거나
   공백만 있는 할 일을 추가하려고 시도하면, **Then** 시스템은 추가를 거부하고 목록은
   변경되지 않는다.
3. **Given** 항목이 여러 개 있는 목록, **When** 사용자가 목록 화면을 연다, **Then**
   추가된 모든 할 일의 제목과 완료 여부가 표시된다.

---

### User Story 2 - 완료 여부 토글 (Priority: P2)

사용자는 목록에 있는 특정 할 일의 완료 상태를 미완료 ↔ 완료로 전환할 수 있다.

**Why this priority**: 완료 표시는 할 일 관리 앱의 핵심 상호작용이지만, 추가/조회
기능이 먼저 동작해야 의미가 있으므로 두 번째 우선순위다.

**Independent Test**: 이미 존재하는 할 일 하나를 선택해 완료 토글을 실행한 뒤,
해당 항목의 상태가 반대로 바뀌어 표시되는지 확인하는 것만으로 독립적으로 테스트할
수 있다.

**Acceptance Scenarios**:

1. **Given** 미완료 상태의 할 일이 목록에 있음, **When** 사용자가 해당 항목의 완료
   토글을 실행하면, **Then** 해당 항목은 "완료" 상태로 표시된다.
2. **Given** 완료 상태의 할 일이 목록에 있음, **When** 사용자가 해당 항목의 완료
   토글을 다시 실행하면, **Then** 해당 항목은 "미완료" 상태로 되돌아간다.
3. **Given** 이미 삭제되어 더 이상 존재하지 않는 할 일, **When** 사용자가 해당
   항목에 대해 토글을 시도하면, **Then** 시스템은 오류를 반환하고 목록 상태는
   변경되지 않는다.

---

### User Story 3 - 할 일 삭제 (Priority: P3)

사용자는 더 이상 필요 없는 할 일을 목록에서 영구적으로 제거할 수 있다.

**Why this priority**: 삭제는 목록을 정리하는 데 유용하지만, 추가·조회·완료 토글이
갖춰진 뒤에도 앱은 독립적으로 가치를 제공할 수 있으므로 세 번째 우선순위다.

**Independent Test**: 목록에 있는 할 일 하나를 삭제한 뒤, 그 항목이 더 이상 목록에
나타나지 않는지 확인하는 것만으로 독립적으로 테스트할 수 있다.

**Acceptance Scenarios**:

1. **Given** 목록에 할 일이 하나 이상 있음, **When** 사용자가 특정 항목을 삭제하면,
   **Then** 해당 항목은 목록에서 더 이상 보이지 않고 나머지 항목은 그대로 유지된다.
2. **Given** 이미 삭제되어 더 이상 존재하지 않는 할 일, **When** 사용자가 같은
   항목을 다시 삭제하려고 시도하면, **Then** 시스템은 오류를 반환하고 목록 상태는
   변경되지 않는다.

---

### User Story 4 - 할 일 중요도 지정 및 확인 (Priority: P4)

사용자는 할 일을 추가할 때 중요도(높음/보통/낮음)를 지정할 수 있고, 목록에서 각
할 일 카드에 표시된 중요도를 확인할 수 있다.

**Why this priority**: 중요도 표시는 기존 추가·조회·토글·삭제 흐름을 보강하는
부가 기능으로, 핵심 CRUD 흐름(P1~P3)이 먼저 갖춰진 뒤에도 독립적으로 추가할 수
있다.

**Independent Test**: 중요도를 "높음"으로 지정해 할 일을 추가한 뒤, 목록에서 해당
항목에 "높음"이 표시되는지 확인하는 것만으로 독립적으로 테스트할 수 있다.

**Acceptance Scenarios**:

1. **Given** 할 일 추가 화면, **When** 사용자가 중요도를 "높음"으로 선택해 할 일을
   추가하면, **Then** 목록에 해당 항목이 "높음" 중요도와 함께 나타난다.
2. **Given** 할 일 추가 화면, **When** 사용자가 중요도를 선택하지 않고 할 일을
   추가하면, **Then** 해당 항목은 기본값 "보통" 중요도로 추가된다.
3. **Given** 할 일 추가 화면, **When** 사용자가 정의되지 않은 중요도 값을 지정해
   추가를 시도하면, **Then** 시스템은 추가를 거부한다.

---

### Edge Cases

- 제목이 공백뿐이거나 비어 있는 상태로 할 일을 추가하려 하면 어떻게 되는가? → 거부
  되어야 한다.
- 목록에 할 일이 하나도 없을 때 목록 화면은 어떻게 보여야 하는가? → 빈 목록임을
  분명히 알 수 있는 상태로 표시되어야 한다.
- 이미 삭제된 항목에 대해 완료 토글이나 삭제를 다시 시도하면 어떻게 되는가? →
  오류를 반환하고 다른 항목에는 영향을 주지 않는다.
- 제목이 매우 긴 할 일을 추가하려 하면 어떻게 되는가? → [Assumptions] 참고.
- 정의된 3단계(높음/보통/낮음)에 속하지 않는 중요도 값으로 할 일을 추가하려 하면
  어떻게 되는가? → 거부되어야 한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 사용자가 제목을 입력해 새로운 할 일을 추가할 수 있도록
  해야 한다.
- **FR-002**: 시스템은 할 일 생성 시 제목이 비어 있거나 공백만 있는 경우 생성을
  거부해야 한다(제목은 필수 항목).
- **FR-003**: 시스템은 새로 생성되는 모든 할 일에 기본값으로 "미완료" 상태를
  부여해야 한다.
- **FR-004**: 시스템은 현재 존재하는 모든 할 일 항목의 제목과 완료 여부를 포함한
  목록을 조회해 보여줘야 한다.
- **FR-005**: 사용자는 특정 할 일 항목의 완료 상태를 완료 ↔ 미완료로 전환할 수
  있어야 한다.
- **FR-006**: 사용자는 특정 할 일 항목을 목록에서 영구적으로 삭제할 수 있어야
  한다.
- **FR-007**: 시스템은 할 일 항목을 지속적으로 저장해, 별도의 세션이나 재방문
  이후에도 목록이 유지되도록 해야 한다.
- **FR-008**: 시스템은 추가·완료 토글·삭제 작업이 성공적으로 처리된 직후 목록에
  그 변경 사항을 반영해야 한다.
- **FR-009**: 시스템은 이미 존재하지 않는(예: 이미 삭제된) 할 일에 대한 완료 토글
  또는 삭제 요청을 거부하고, 목록 상태를 변경하지 않은 채 오류로 처리해야 한다.
- **FR-010**: 시스템은 이미 생성된 할 일의 제목을 수정(이름 변경)하는 기능을
  제공하지 않는다(범위 외). 제목을 바꾸려면 기존 항목을 삭제하고 새 항목을
  추가해야 한다.
- **FR-011**: 시스템은 서로 다른 할 일 항목 간 제목 중복을 허용해야 하며, 제목이
  아닌 내부 고유 식별자로만 각 항목을 구분해야 한다.
- **FR-012**: 시스템은 각 할 일 항목에 중요도(높음/보통/낮음 중 하나) 속성을
  부여하고, 목록에서 각 항목의 중요도를 확인할 수 있도록 해야 한다.
- **FR-013**: 시스템은 할 일 생성 시 사용자가 중요도를 지정하지 않으면 기본값
  "보통"을 부여해야 한다.
- **FR-014**: 시스템은 정의된 3단계(높음/보통/낮음)에 속하지 않는 중요도 값으로
  할 일을 생성하려는 요청을 거부해야 한다.

### Key Entities *(include if feature involves data)*

- **할 일(Todo Item)**: 사용자가 관리하는 작업 단위를 나타낸다. 제목(문자열, 필수,
  비어 있을 수 없음, 다른 항목과 중복 가능), 완료 여부(불리언, 기본값 미완료),
  중요도(높음/보통/낮음 중 하나, 기본값 보통) 속성을 가지며, 각 항목을 다른
  항목과 구분할 수 있는 고유 식별자를 갖는다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 사용자는 10초 이내에 새로운 할 일 하나를 추가할 수 있다.
- **SC-002**: 추가된 할 일의 100%가 별도의 새로고침 조작 없이 목록에 정확히
  나타난다.
- **SC-003**: 사용자는 한 번의 조작(예: 클릭/탭 1회)으로 할 일의 완료 상태를
  전환할 수 있다.
- **SC-004**: 사용자는 한 번의 조작으로 원하지 않는 할 일을 삭제할 수 있고,
  삭제 직후 해당 항목은 목록에서 즉시 사라진다.
- **SC-005**: 추가·토글·삭제 작업을 연속으로 100회 수행해도 목록에는 항목의
  누락이나 중복 없이 실제 수행한 작업이 100% 정확히 반영된다.

## Assumptions

- 이 기능은 단일 사용자 환경을 가정하며, 별도의 로그인/인증 절차는 이 기능
  범위에 포함되지 않는다.
- 할 일 항목은 메모리가 아닌 지속 저장소에 보관되어 세션이 종료되어도 유지된다.
- 각 할 일 항목은 시스템이 내부적으로 부여하는 고유 식별자를 가지며, 이는
  사용자에게 노출되는 필드가 아니다.
- 목록의 기본 정렬 순서는 별도 지정이 없는 한 생성된 순서를 따른다.
- 사용자가 생성할 수 있는 할 일 개수에는 이 기능 범위 내에서 별도의 상한을 두지
  않는다.
- 할 일 제목의 길이 상한은 일반적인 한 줄 텍스트 입력 수준(예: 200자 내외)으로
  가정하며, 이를 초과하는 매우 긴 제목은 거부될 수 있다.
- 삭제는 즉시 영구적으로 처리되며, 이번 기능 범위에서는 "실행 취소" 기능을
  제공하지 않는다.
- 중요도는 생성 시에만 지정하며, 이번 기능 범위에서는 생성 이후 중요도를
  변경하는 기능은 제공하지 않는다(제목과 마찬가지로 변경하려면 삭제 후 재생성).
